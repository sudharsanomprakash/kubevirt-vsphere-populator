# Design: source format, export protocol and conversion

This document records what the implementation relies on and how strong the
evidence for each point is. It was written without access to a real vCenter
or ESXi host. Everything below that depends on real vSphere behavior is marked,
and the corresponding checks are listed as unpassed release gates in
[release-checklist.md](release-checklist.md).

Evidence levels used below:

| Label | Meaning |
|---|---|
| **Documented** | Stated in VMware API reference material or in govmomi source code (v0.56.0) |
| **VMware sample** | Observed in a streamOptimized VMDK generated by VMware software (`iotest-version3.vmdk`, from the QEMU test suite; fetched by `hack/fetch-fixtures.sh`) |
| **Fake** | Behavior of this project's test double (`test/fakevsphere`), which models the documented behavior; it is not evidence about vSphere |
| **Unverified** | Not yet observed on a real vCenter/ESXi; use `vsphere-populator-worker diagnose` to capture it |

## 1. The HttpNfcLease export protocol

1. `ExportVm` on a VirtualMachine returns an `HttpNfcLease`. The lease starts
   in `initializing` and moves to `ready` (with `info` populated) or `error`
   (with `error` populated). **Documented.** The worker waits for this with a
   property collector wait and a bounded timeout, and aborts the lease if it
   does not become ready in time.
2. `HttpNfcLeaseInfo` carries `lease`, `entity`, `deviceUrl[]`,
   `totalDiskCapacityInKB` and `leaseTimeout` (seconds). **Documented.**
3. Each `HttpNfcLeaseDeviceUrl` carries `key`, `importKey`, `url`,
   `sslThumbprint`, `disk`, `targetId`, `datastoreKey` and `fileSize`.
   **Documented.** VMware's reference shows keys of the form
   `/vm-10649/VirtualLsiLogicController0:0` and target IDs such as
   `disk-1.vmdk`, and states that for exports a single device ID based on
   object identifiers is returned. The URL host may be `*`, which the client
   must replace with the host it connected to (govmomi's `Client.ParseURL`
   does this). When connected through vCenter the URL points at the ESXi host
   that serves the disk, and `sslThumbprint` is that host's certificate
   thumbprint. **Documented.**
4. The lease must be renewed with `HttpNfcLeaseProgress(percent)` within
   `leaseTimeout`, otherwise it expires. **Documented.** govmomi's
   `nfc.LeaseUpdater` (v0.56.0, `nfc/lease_updater.go`) logs a failed renewal
   and stops renewing, without telling the caller. This project therefore uses
   its own keepalive (`internal/vsphere/lease.go`): it renews every
   `min(10s, leaseTimeout/6)` (at least 1s), treats `ManagedObjectNotFound`,
   `InvalidState`, `Timedout`, `NotAuthenticated` and `NoPermission` as fatal,
   tolerates up to three consecutive transient failures, and cancels the
   transfer when it gives up.
5. `HttpNfcLeaseComplete` marks success; `HttpNfcLeaseAbort(fault)` marks
   failure. `HttpNfcLeaseGetManifest` returns `HttpNfcManifestEntry` records
   with `key`, `size`, `sha1` and, on newer releases, `checksum` and
   `checksumType`. **Documented.** Whether a real export manifest carries a
   checksum for the stream just downloaded, and with which algorithm, is
   **Unverified**; the worker verifies SHA-1 or SHA-256 when present, records
   `unavailable`/`no-entry`/`no-checksum` otherwise, and can be told to fail
   in that case (`spec.transfer.requireManifest`).

### vcsim is not a model of exports

govmomi's simulator (vcsim) implements `ExportSnapshot` and `ImportVApp`
leases but not `ExportVm`, its device keys look like `/vm-42/disk:0`, and its
manifest only covers uploads. The test double in `test/fakevsphere` therefore
adds an `ExportVm` implementation with documented-format keys, lease states,
expiry without renewal, manifests, and injectable faults. The worker rejects
vcsim-style keys (tested).

## 2. What an export URL serves

**It is a streamOptimized VMDK, not raw guest bytes.**

* govmomi transfers disks through NFC leases as
  `application/x-vnd.vmware-streamVmdk` (`nfc/lease.go`, `Lease.Upload`), and
  OVF/OVA exports contain streamOptimized VMDKs. **Documented.**
* The VMware-generated sample has this layout (**VMware sample**, see
  `internal/vmdk/interop_test.go`):

  | Field | Value |
  |---|---|
  | magic | `KDMV` (0x564d444b) |
  | version | 3 |
  | flags | 0x30001 (valid newline test, compressed grains, markers) |
  | capacity | 33554432 sectors (16 GiB) |
  | grain size | 128 sectors (64 KiB) |
  | descriptor | 1 sector at sector 1, `createType="streamOptimized"`, one `SPARSE` extent |
  | gdOffset in header | 0xffffffffffffffff (grain directory at the end) |
  | overhead | 128 sectors |
  | compression | 1 (deflate, zlib framing) |
  | body | 100 grain markers in ascending LBA order, each grain table marker (4 sectors) after the grains it covers, then one grain directory marker, one footer marker with a footer header that locates the grain directory, and an end-of-stream marker |

* Exported bytes have no fixed relationship to guest offsets: grains are
  compressed and variable-length, and unallocated grains are absent.
  Writing exported bytes at the same offsets of a device would corrupt the
  disk. This project never does that.
* Range requests: the stream is generated and compressed on the fly, so
  whether ESXi honors `Range` is **Unverified**. The populator does not use
  Range at all; it reads each disk sequentially with a single GET. The
  `diagnose` command reports whether a `Range: bytes=512-1023` request returns
  206 with the same bytes as a plain request.
* `Content-Length` may or may not be present (**Unverified**). If it is, a
  short body is rejected. Either way, completeness is established by the VMDK
  structure (footer, grain directory and end-of-stream marker), because a
  cancelled or cut-off chunked response can end with a well-formed terminator.
* Parallel GETs of the same URL: not used. No claim is made that parallel
  requests bypass any ESXi throttle.

### qemu-img's streamOptimized files differ

`qemu-img convert -O vmdk -o subformat=streamOptimized` (8.2.2) writes the
grain directory into the overhead area (header `gdOffset` set), and writes
neither a footer nor an end-of-stream marker. Such a file cannot be checked for
truncation at a grain boundary, so the decoder rejects it
(`TestRejectsQemuFileLayout`). qemu-img *reads* both layouts; the test encoder
in `internal/vmdk/writer.go` produces the VMware layout and qemu-img converts
it back to the original bytes (`TestQemuReadsOurStreams`).

## 3. Selecting the disk

Source identity (exactly one): managed object reference, instance UUID,
BIOS UUID or name. BIOS UUIDs and names are accepted only when they match
exactly one VM (names are compared exactly after the property filter, which
treats names as glob patterns).

Disk identity (exactly one): device key, bus location
(`scsi|sata|nvme|ide:<bus>:<unit>`) or backing file name. An optional
expected capacity is cross-checked.

Rejected configurations: VM not powered off, not connected, with snapshots,
encrypted; disks with RDM or unknown backings, delta (parent) backings,
non-`persistent` modes (including `independent_persistent`, whose export
behavior has not been verified), multi-writer sharing, encryption, or a
capacity that is not a positive multiple of 512.

Mapping the selected disk to a lease URL:

1. The expected key is `/<vm moref>/<controller Go type name><bus number>:<unit>`,
   for example `/vm-42/VirtualLsiLogicController0:1` or
   `/vm-42/VirtualNVMEController0:0`.
2. The documented example does not show whether the controller number is the
   controller's bus number or its index among controllers of the same type.
   The two coincide in common layouts. When they differ (for example an LSI
   Logic controller on bus 0 and a ParaVirtual controller on bus 1) the disk is
   rejected rather than guessed. **Unverified** on real vSphere.
3. Every disk URL must parse and name this VM, the number of disk URLs must
   equal the number of VM disks, and exactly one URL must carry the expected
   key. There is no fallback to URL order.
4. The VM is re-read after the lease is ready and again before the lease is
   completed; a change of power state, `config.changeVersion`, snapshot state
   or the selected disk fails the population.

## 4. Conversion

The stream is staged to a bounded file and converted by the pinned
`qemu-img` (Ubuntu `qemu-utils` 1:8.2.2+ds-0ubuntu1.18, GPL-2.0-or-later, run
as a subprocess). This is **staged conversion**, not streaming and not
zero-copy:

* qemu-img needs a seekable file, and streamed exports place the grain
  directory at the end.
* A Go streaming writer is feasible, but without real-export tests it would
  be the only thing standing between the stream and the disk. Instead the Go
  decoder is used as an independent *verifier*: two implementations (qemu-img
  writing, Go decoding) must agree.

Staging: before the lease is requested, the staging filesystem must have at
least 1 MiB free, and writes stop at the configured limit (default: available
space minus 64 MiB). Stale staging files from interrupted attempts are
removed at start, and the staging file is removed on every exit path. In
Kubernetes the scratch volume is an `emptyDir` with a size limit or a generic
ephemeral PVC, sized to the PVC request plus 2% plus 256 MiB.

Destinations:

* **Filesystem PVC**: qemu-img creates `disk.img.partial` (a new, sparse
  file) in the volume root; after flush and verification it is renamed to
  `disk.img` and the directory is fsynced. A previous `disk.img` is replaced
  atomically and its old bytes are never reused. The filesystem must have
  free space for the full virtual size. An advisory `flock` guards against a
  second writer.
* **Block PVC**: the device is opened with `O_EXCL` (a concurrent exclusive
  open or mount on the same node fails), its size must be at least the
  virtual size, and qemu-img writes with `-n` (existing target). qemu-img does
  not assume the target reads as zeros, so zero regions of the source are
  written as zeros. The project never passes `--target-is-zero`; doing so on
  a prefilled target leaves old bytes behind (checked by hand while building
  this; the tests assert the flag is absent and that prefilled targets are
  cleared). Bytes beyond the virtual size are cleared with `BLKZEROOUT`
  (falling back to writing zeros), then the device is fsynced.

## 5. Validation chain

A population is reported as validated only when all of these hold:

1. HTTP 200, no content encoding, body length equal to `Content-Length` when present.
2. The stream parses completely: valid header and descriptor
   (`streamOptimized`, one extent equal to the capacity), every grain aligned,
   inside the capacity, not duplicated, decompressing (with a valid Adler-32)
   to exactly one grain, known metadata markers, a footer consistent with the
   header, a grain directory, an end-of-stream marker, and only zero padding
   after it.
3. The header's virtual size equals the vSphere disk capacity (checked before
   the body is downloaded).
4. The staged byte count equals the decoded byte count, and the manifest
   checksum matches when available.
5. `qemu-img info` sees a vmdk with the same virtual size.
6. After conversion and flush, the destination is read back (with `O_DIRECT`
   when available, otherwise after `POSIX_FADV_DONTNEED`) and its digest
   equals the digest computed by the Go decoder from the stream.
7. The source VM is unchanged.

Only then is the lease completed. Any failure aborts it.

The digest is a chunked SHA-256 (`internal/digest`): SHA-256 over the
concatenation of per-MiB SHA-256 values, prefixed by the length. It lets
all-zero regions be hashed cheaply. `vsphere-populator-worker digest` computes
it for any file or device.

What this proves: the destination holds exactly what the Go decoder reads out
of the stream that vSphere served. It does not by itself prove that the stream
matches the source disk; the manifest checksum (when available) covers
transfer integrity, and the end-to-end test compares the destination with the
source raw image using plain `sha256sum`, independently of the populator's
own digests.

## 6. Performance characteristics

* One sequential GET per disk. Throughput is bounded by the ESXi NFC server,
  the network, and single-threaded zlib decoding in the worker.
* Local I/O is roughly: stream written once to staging and read by qemu-img,
  and the destination written once and read back once in full.
* No throughput numbers against vSphere exist yet. The local pipeline
  baseline is in [benchmarks.md](benchmarks.md).
